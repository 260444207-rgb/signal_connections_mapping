# 现有 Skill 加入 Workflow Checkpoint 卡点的改造要求

本文用于指导开发者或实施 Agent 改造已有 `SKILL.md`，使其接入 `workflow-checkpoint` 插件。保留 Skill 原有业务目标、执行要求、工具限制和交付标准，只增加阶段定义、完成条件、交接卡点和恢复规则。

适用流程：

```text
阶段完成 → 本地归档完整上下文 → 提取用户输入、完成状态和中间产物
→ 保存启动 prompt → 等待当前 run 结束 → reset 原会话上下文
→ 在原任务窗口发送启动 prompt → 执行下一阶段
```

本文对应具有 `sessions.reset` 能力的新版插件。仅有状态注入功能的旧版插件不满足上述流程；先核对安装版本，不能仅凭 Skill 文案宣称已经重置上下文。

## 1. 职责边界

- Skill 决定阶段如何划分、何时完成、在哪里调用卡点。
- 插件负责归档、结构化状态提取、持久化、会话重置和后续 run 调度。
- 卡点必须是实际调用 `workflow_checkpoint`，不是输出同名 JSON，也不是说一句“阶段完成”。
- 不允许 Skill 自行调用 reset、创建新任务或子会话来代替插件交接。
- Skill 不需要生成长篇交接总结；应明确关键结果、实际产物路径和遗留问题，让插件能从上下文提取。

## 2. 改造前先审阅原 Skill

实施者必须先读取完整 Skill 及其引用的工作流说明，识别：

1. 原始输入、交付物和验收标准。
2. 已有步骤及其依赖顺序。
3. 哪些步骤能独立完成并形成稳定产物。
4. 下一步依赖哪些文件、数据、决策和约束。
5. 是否存在审批、循环、回滚或条件分支。

不要机械地在每个标题后插入 checkpoint。一个尚未完成的写文件操作、仍在执行的并行任务、需要共享临时内存的连续操作，不适合作为卡点。

当前插件只校验配置中的线性阶段序列。遇到条件分支、循环或回滚要求时，应先调整设计；不能擅自删掉原业务逻辑，也不能把未执行的阶段标为完成来凑齐序列。

## 3. 声明 workflow 和阶段

为工作流定义稳定的 `workflow_id`，为每个阶段定义明确的 `stage_id`。A、C、D 只是示例，可以换成业务名称。

标识使用字母或数字开头，后续允许字母、数字、点、下划线和连字符，总长度不超过 128。建议统一使用小写英文。

示例插件配置片段，位于 `plugins.entries.workflow-checkpoint.config`：

```json
{
  "workflows": {
    "research-report": ["research", "draft", "review"]
  }
}
```

在 Skill 中增加：

```markdown
## Workflow

- workflow_id: research-report
- 阶段顺序：research → draft → review
- 首次执行且没有恢复状态时，从 research 开始。
- 恢复执行时，从 continuation.next_stage 指定的阶段继续。
```

`workflow_id` 必须已配置；阶段名称、大小写和顺序必须与配置一致。插件不会自动解析 Skill 的标题生成配置，也不允许模型自由选择跳到任意阶段。

同一业务会话内重复执行完整流程，目前需要配置新的 workflow ID；不要编造插件尚未配置的随机 ID，也不要使用不存在的 `completion_version` 或 `rollback` 工具参数。

## 4. 每个阶段必须具备的四项内容

### 4.1 进入条件

说明首次执行还是从 checkpoint 恢复，以及本阶段需要哪些前置结果。恢复时以结构化状态中的阶段进度为准，不因为旧聊天仍在界面上显示就重新执行已完成阶段。

### 4.2 业务步骤

保留原 Skill 的任务要求、工具使用约束和质量标准。卡点改造不能降低原有完成标准。

### 4.3 可验证的完成条件

至少明确：

- 本阶段必做工作已经完成。
- 必需产物已成功写入，实际路径已知。
- 下一阶段需要的信息已经可从文件或当前上下文取得。
- 必须解决的阻塞项已经处理；不能用 completed 隐藏失败。
- 所有本阶段工具已返回，不存在仍在进行的异步写入。

### 4.4 显式卡点及停止规则

所有完成条件满足后，单独调用 checkpoint。不要与其他工具并行调用；成功后立即结束当前 run，下一阶段由插件重启上下文后进入。

## 5. 可复制的阶段卡点模板

把下面模板插入原 Skill 的实际阶段末尾，并替换业务步骤与标识：

````markdown
## 阶段 research：资料研究

### 进入条件
- 首次执行且没有 checkpoint；或恢复状态指定当前阶段为 research。

### 执行内容
- 按原 Skill 要求完成资料收集和分析。
- 将后续阶段需要的结果保存为本地文件。
- 在上下文中明确实际文件路径、用途以及仍存在的不确定项。

### 完成条件
- 所有必需研究任务已完成。
- 结果文件已保存且可读取。
- 下一阶段所需信息齐备。
- 本阶段所有工具已返回。

### Checkpoint
满足上述条件后，单独调用实际工具 workflow_checkpoint：

```json
{
  "workflow_id": "research-report",
  "stage_id": "research",
  "status": "completed",
  "next_stage": "draft",
  "reason": "stage_boundary"
}
```

根据工具的实际返回结果处理：
- ok=true：结束当前 run，不开始 draft，不再调用工具。
- ok=false：不推进阶段，按失败处理规则处理。
- duplicate=true：不要重做本阶段或再次触发重置；结束当前 run。

下一阶段由插件在原任务窗口 reset 上下文并发送启动 prompt 后启动。
````

## 6. 在 Skill 顶部加入恢复执行规则

```markdown
## Checkpoint 恢复规则

1. 先判断启动 prompt 是否含有 workflow continuation state。
2. 没有恢复状态时，从配置中的第一个阶段开始。
3. 有恢复状态时，读取：
   - original_user_inputs：原始用户输入和补充要求；
   - objective：目标与验收条件；
   - progress.completed_stages / remaining_stages：阶段完成情况；
   - continuation.next_stage：本轮要执行的阶段；
   - state：成果、决策、约束和阻塞项；
   - artifacts / next_stage_context：产物与下一阶段所需信息。
4. 只执行指定阶段，不能自动重跑已完成阶段。
5. 需要详细数据时读取对应产物，不默认重读完整历史归档。
6. 若缺少本 Skill 的步骤说明，先读取已知路径的 SKILL.md；不得凭空猜测。
7. 用户新要求优先；发现其使原流程无效时，停止推进并说明冲突。
8. completed 阶段产物确实失效时，不擅自回滚；报告问题并等待流程调整。
```

改造时应确保 Skill 能通过现有安装方式在重置后再次发现。若依赖额外流程文件，应保留其稳定路径与引用关系，并让读取工具的实际输出中包含这些路径；不能只依靠 A 阶段的临时记忆。

## 7. 中间产物要求

本规范中的“中间产物”包括文件、结构化数据、关键结论以及下一阶段的执行前提。

建议在阶段结束前明确：

```text
产物：实际生成的 analysis.json
实际路径：由文件工具确认的路径
用途：下一阶段据此编写报告
关键结论：已经验证的结果
未决项：仍需下一阶段处理的问题
```

不得声明不存在的文件，也不要只写“分析完成，见上文”。reset 后下一阶段不自动拥有 A 的完整历史。

`state_hint` 可选，支持 `completed`、`decisions`、`artifacts`、`blockers`、`notes` 字符串数组。它只是提取提示，不是权威状态，不可用于伪造阶段进度或代替产物落盘。每个数组最多 50 项，每项最多 2000 字符。

## 8. 最后一个阶段

最后阶段完成时省略 `next_stage`：

```json
{
  "workflow_id": "research-report",
  "stage_id": "review",
  "status": "completed",
  "reason": "stage_boundary"
}
```

成功后可直接发送最终交付说明，然后结束 run，不再调用工具。该卡点会归档并完成 workflow，不 reset 启动不存在的下一阶段。

## 9. 失败、暂停和重复调用

| 情况 | Skill 的处理要求 |
|---|---|
| 工具不可用 | 停在阶段边界，明确报告配置/工具问题；不自行 reset，不进入下一阶段 |
| ok=false 且 retryable=true | 保留当前进度，允许有限次重试 checkpoint；不得无限循环或重做已完成业务工作 |
| ok=false 且 retryable=false | 报告错误码，停止推进，修正流程或配置后再继续 |
| ok=true 且 duplicate=true | 视为卡点已处理；不重复执行阶段，不通过重复调用强制重启 |
| 必需产物未生成或验证未通过 | 不提交 completed；继续处理本阶段问题或明确暂停/失败 |
| completed 后的交接请求失败 | 不自行创建新会话；保留归档与启动 prompt，由原会话恢复流程处理 |

需要保存暂停状态时：

```json
{
  "workflow_id": "research-report",
  "stage_id": "research",
  "status": "paused",
  "reason": "manual",
  "state_hint": { "blockers": ["等待用户提供必要输入"] }
}
```

`paused` / `failed` 都不传 `next_stage`，不会把本阶段标记完成，也不会自动 reset 续跑。调用成功后同样结束 run；后续本阶段实际完成后再提交 completed。它们不是自动等待审批的调度器。

## 10. 实施者应交付的改动

1. 改造后的 `SKILL.md`，保留原业务内容，加入流程声明、各阶段完成条件、卡点和恢复规则。
2. 与 Skill 完全一致的插件 `workflows` 配置片段。实际修改配置时应合并现有内容，不能覆盖其他工作流。
3. 中间产物的交接约定：路径如何取得、用途是什么、下一阶段如何读取。
4. 一份简短改造说明：哪些位置新增卡点，哪些逻辑因线性阶段限制尚不能适配。

## 11. 验收清单

- [ ] 阶段名称及顺序与插件配置一致，未写死必须使用 A/C/D。
- [ ] 每个非最终阶段都有明确且可验证的完成条件。
- [ ] 调用的是实际工具，不是仅输出 JSON 或自然语言声明。
- [ ] checkpoint 单独调用，所有前置工具已结束。
- [ ] completed 卡点的 next_stage 是配置中的直接下一阶段。
- [ ] 成功或重复卡点后结束当前 run，不继续执行下一阶段。
- [ ] reset 后仅凭用户输入、提取状态和产物即可开始下一阶段。
- [ ] 原 Skill 及必要引用文件能在 reset 后重新发现。
- [ ] 必需产物缺失时不会误报 completed。
- [ ] 暂停/失败不会被当作阶段完成。
- [ ] 最终阶段不传 next_stage，不再启动后续阶段。
- [ ] 不要求模型传 session identity、长总结或未支持的工具参数。
- [ ] 已在测试任务验证归档文件、启动 prompt、真实 reset 和下一阶段进入情况。

静态修改 Skill 完成，不等于真实 Gateway 的端到端验收完成。最终应验证原任务窗口保留、模型上下文已 reset，且下一阶段没有重复执行已完成工作。
